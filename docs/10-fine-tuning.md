# Fine-tuning

Status as of 2026-07-30: **nothing has been trained.** A GPU node was provisioned and
stopped, a dataset exists and is under review, no weights have been produced.

## Why tune at all

Not to improve the voice. The prompt already produces the target voice most of the time,
and where it doesn't, `voiceCheck.ts` catches it. Tuning can't beat that ceiling because
the dataset is generated by that same pipeline.

The actual prize is **prompt compression**. The full system prompt is ~10,300 characters.
Strip the static voice instruction and keep only per-user context (date, natal chart,
today's transits, saved places, wardrobe) and it's ~1,900. That's an 81% reduction on every
single request, and the voice lives in the weights instead of depending on a small model
correctly honouring forty negative constraints every time.

Set expectations accordingly: cheaper and faster, not smarter.

## Where the data comes from

`lib/trainingData.ts` records every turn: the prompt, the model's unaided first draft, the
violations the checker found, and the response that actually shipped. Off unless
`PINCH_TRAINING_LOG` is set.

This works because the checker is a **deterministic labelling function**. No human sits
there rating outputs; a violation is a label. Every message Pinch answers is a free
training example.

`scripts/collect-training.ts` drives synthetic conversations to build a corpus faster than
real traffic would. Two things it deliberately does:

- **Eight different birth charts** across decades and timezones. One chart would teach the
  model that chart's placements rather than the voice.
- **Message types weighted away from advice requests.** A corpus of only "should I..."
  questions would teach the model to give advice to everything, which is the exact failure
  mode the voice rules design out.

`scripts/export-training.ts` converts to Gemini, OpenAI, ChatML or DPO format.
`--minimal-prompt` does the prompt stripping described above.

New captures include a one-way conversation fingerprint. Export with `--split train` and
`--split validation`; all rows from one conversation stay on one side of the boundary.
This prevents a validation score from being inflated by seeing the same person's chart
and conversational context during training. Legacy rows fall back to grouping by their
full prompt context. The exporter also rejects every shipped response that fails the
current deterministic voice checker—rewritten examples are kept only when the rewrite
actually landed cleanly.

## What the dataset actually is

**Synthetic self-distillation.** Invented users texting the live pipeline. Not real
iMessages (not accessible, see [09-integrations.md](09-integrations.md)) and not a scraped
corpus (see below). Its ceiling is the current prompt's behaviour.

Real conversation history does exist in the Convex `chats` table. It's genuinely better
material and has not been used, because it's real user content and needs a deliberate call.

## Two filtering bugs worth remembering

**Filter on the shipped response, not the first draft.** The first exporter kept only
turns that were clean on the first attempt, discarding every turn that needed a rewrite.
But a turn that was corrected and ended clean is a perfectly good example of the target
voice. Fixing this roughly doubled the usable corpus.

**Apply deterministic transforms at export.** Casing mirroring landed partway through
collection, so early examples carry the model's random casing. Re-deriving it at export
means the whole corpus is consistent rather than only the turns collected after a
particular moment.

## Quality, measured 2026-07-30

192 examples, of which 159 clean. The flagged 33:

| Issue | Count |
|---|---|
| Mood narration | 15 |
| Names a placement | 10 |
| Onboarding turns | 9 |
| Dismissive to distress | 2 |

The flags only catch what a pattern can catch. "im scared" answered with "just push past
it" was only caught because a rule was written for that exact phrasing after someone
noticed it. Assume more of that kind exists.

**A fine-tune reproduces the corpus exactly, flaws included.** Right now a bad output gets
caught and rewritten; after training these become the default. That is the argument for
curating rather than collecting more.

## Compute

**givemeanode**, MCP-based GPU orchestrator, connected via
`claude mcp add --transport http givemeanode https://mcp.givemeanode.com`.

$500 in credits. One H100 is $0.06/min ($3.60/hr) with a 15-minute minimum. Node named
`pinch-tune` exists and is **stopped**; files survive stopping and the next command wakes
it. Total spend so far is about $0.90.

`train_pinch.py` is on the node: LoRA on Qwen2.5-7B-Instruct, r=32, loss on the reply only
so capacity doesn't go into reproducing the system prompt. LoRA rather than full
fine-tuning because a few hundred examples of full-weight training mostly produces
forgetting.

**Stop the node the moment it isn't working.** It bills while idle.

## The checker stays either way

Tuning shifts a distribution, it doesn't guarantee anything. `voiceCheck.ts` remains the
floor that stops an em-dash reaching a user. If a tune works, violation rates drop and it
shows directly in the export statistics.
